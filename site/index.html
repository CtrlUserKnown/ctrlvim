> Neovim's core, rewritten in Rust. Same modes, same motions, zero C.
ctrlvim is a from-scratch Rust reimplementation of Neovim's editing
engine — rope buffers, the mode state machine, the ex-command layer,
a real Vim regex engine, a Lua runtime — with a Ratatui-powered
terminal frontend on top. The binary is cvi.

# About ctrlvim
> A reimplementation of Neovim's editing model, not a wrapper around it.
## Why
Neovim is incredible, and its C core is a mountain of complexity.
Reading it to change one behavior means paging in decades of history.
ctrlvim rebuilds that core in memory-safe Rust, one concern per crate,
keeping what makes Vim good — modal editing, extensibility, a
terminal-native feel — while making the internals something you can
read in an afternoon. If you know Vim, you already know how to drive
it: d2w, ci", qa…q and @a, `m, <C-o>, zf, :%s/old/new/g all
mean what you expect.
What's different is everything around the buffer: a project dashboard,
a fuzzy finder, a live find-&-replace panel, a command palette, pinned
files, and a TOML config file instead of a config script.
## The one invariant
╭──────────────────────────────────────────────────────────────────╮
│ The engine owns the data; the host owns the I/O. │
│ │
│ ctrlvim-editor is UI-less. It moves the cursor for :5 itself, │
│ but anything touching the filesystem, the window list or │
│ process lifetime is emitted as an ExEffect for the frontend │
│ to carry out. The engine decides what; the host does it. │
╰──────────────────────────────────────────────────────────────────╯
That split is why the editor is testable without a terminal, and why
"editor logic belongs in the engine" is a rule rather than a
preference — shortcutting a feature into the TUI makes it unlistable,
unbindable and untestable.
Two consequences worth stating outright:
1. Everything is an ex-command. The palette, the drawer, the
plugin manager and the help modal are ExEffect::HostActions,
not hardcoded key handlers. That is what makes <leader>p
expressible at all, and what lets ? list it.
2. Config is executed as ex-commands. [options] becomes :set,
[[keymap]] becomes :nnoremap, [[command]] becomes :command.
One code path, one definition of what an option means.

## One line
$ curl -fsSL https://ctrluserknown.github.io/ctrlvim/install.sh | sh
Installs to ~/.local — no root, ever, on its own say-so. It is a
plain POSIX shell script that:
1. checks for git, cargo and a C compiler
2. clones ctrlvim into ~/.cache/ctrlvim/src — or updates it, on
the next run
3. runs make install PREFIX=~/.local — the same target you'd run
by hand, nothing bespoke
4. adds ~/.local/bin to your shell's PATH if it isn't there
Read it before you pipe it — install.sh is under 200 lines and has
no logic of its own to drift out of sync with the Makefile.
Make sure ~/.local/bin is on your PATH:
$ export PATH="$HOME/.local/bin:$PATH"
## System-wide instead
$ sudo sh -c "$(curl -fsSL https://ctrluserknown.github.io/ctrlvim/install.sh)" -- --prefix /usr/local
## From a clone
$ git clone https://github.com/CtrlUserKnown/ctrlvim
$ cd ctrlvim
$ sudo make install # → /usr/local/bin/cvi
$ make install PREFIX=~/.local # no root
$ make user-config # seed config.toml
$ sudo make uninstall # remove it again
make help lists every target; PREFIX, DESTDIR, CARGO, INSTALL,
STRIP, TARGET_DIR and UNIVERSAL are honored.
## macOS
The targets above work as-is and build for the host architecture. For
one binary that runs on both Apple Silicon and Intel:
$ make macos-deps # rustup target add, once
$ make macos # universal, ad-hoc signed
$ sudo make macos-install
## Without installing anything
$ cargo run -p ctrlvim # launch the editor
$ cargo run -p ctrlvim-core # headless demo, no UI
$ cargo test --workspace # run the suite
To build local AI completion in, add --features ai (or ai-cuda /
ai-metal) — see docs → AI Suggestions.
## First run
$ cvi # dashboard for this directory
$ cvi src/main.rs # open a file
$ cvi --version
Then, inside: ? for the whole keymap, : for the command palette,
<Space>e for the fuzzy file browser, <Space>w to write.

## Launching
▏ cvi # dashboard for the current directory
▏ cvi src/ # dashboard for a directory (sets the project root)
▏ cvi a.rs b.rs # open files, cursor in the first
▏ cvi --help # usage
▏ cvi --version
A directory argument sets the project root — what the dashboard, the fuzzy
finder, :Find and the git panel all reflect. With no directory given, that's
the current working directory.

buffer. It has three sections, switched with 1 / 2 / 3 or cycled with
[ / ]:

## Opening files
Four ways, in rough order of how often you'll use them:
1. <Space>e (or <Space>ff) — the fuzzy file browser. Type to filter,
Ctrl-n / Ctrl-p or arrows to move, Enter to open, Esc to cancel.
Typing a name that doesn't exist and pressing Enter creates it.
2. <C-b> — the file drawer, a persistent sidebar. j/k to move,
Enter to open, / to search inside it, Esc to close.
3. :e path/to/file — by name. Bare :e opens the browser.
4. cvi file — from the shell.
## Tabs and buffers
ctrlvim's tabs are its buffer list — :tabnext and :bnext are the same
command. The dashboard is itself a tab, so <Space>d always gets you back to
it.

## Editing, saving, quitting
i enters Insert mode, Esc (or jk) leaves it. Then:
┌───────────┬─────────┬─────────────────────────────────────────┐
│ Key │ Command │ Does │
├───────────┼─────────┼─────────────────────────────────────────┤
│ <Space>w │ :w │ write the buffer │
│ <Space>q │ :wq │ write and quit this window │
│ <Space>qq │ :q! │ quit without saving │
│ │ :qa │ quit every window │
│ │ :close │ close ctrlvim outright │
│ │ Ctrl-C │ emergency quit, honored even mid-insert │
└───────────┴─────────┴─────────────────────────────────────────┘
:q on the last window with unsaved changes will refuse; :q! forces it.
A buffer with no filename yet prompts for one on :w.
If ctrlvim is closed with unsaved changes, the next launch in that project
restores both the open-buffer list and a snapshot of the unsaved text.

## Discovering keys
Press ? for the whole keymap. It is generated from the live mapping
table, so your own [[keymap]] entries appear there with no extra work and a
stale entry is impossible.
Hold a prefix — <Space>, say — and pause: a which-key popup lists what can
follow it. How long it waits is 'timeoutlen' (500 ms by default).

### Not bound by default
Bindings that would shadow a standard Vim motion — H/L (screen top/bottom),
[[/]] (section motions), ; (repeat f/t) — are deliberately not
defaults, so muscle memory keeps working. They ship commented out in
docs/config.example.toml
if you want them.

## Rebinding
▏ [keymaps]
▏ leader = " " # what <leader> expands to
▏ defaults = true # false starts from an empty mapping table
▏
▏ [[keymap]]
▏ mode = "n" # "n" (default), "i", or "v"
▏ lhs = "<leader>g"
▏ rhs = ":Find<CR>"
▏ desc = "Search the project"
▏
▏ [[unmap]] # give a chord back to its Vim meaning
▏ mode = "n"
▏ lhs = "<leader>d"
Both sides use <...> notation: <leader>, <Space>, <Esc>, <CR>,
<Tab>, <S-Tab>, <C-x>, <A-x> (same as <M-x>), <C-S-x>, <Up>,
<C-Left>, <F5>, <Del>, <Home>.
desc is what ? and the which-key popup show. It's optional — an undescribed
mapping is listed by its right-hand side — but it's the difference between a
keymap you can discover and one you have to read your config to understand.
An lhs that doesn't parse is reported on the status line, not silently
ignored, so a typo can't leave you with a dead key.
You can also map at runtime:
▏ :nnoremap <desc=Save file> <leader>w :w<CR>
▏ :inoremap jj <Esc>
▏ :vunmap <
▏ :map " list every normal-mode mapping

## Operators
d delete, y yank, c change, > / < indent right / left, gu / gU /
g~ lowercase / uppercase / toggle case.
An operator takes a motion or a text object:
▏ d2w delete two words
▏ c$ change to end of line
▏ y{ yank back one paragraph
▏ >ip indent this paragraph
▏ gUiw uppercase this word
▏ dd yy cc >> operate on the whole line (doubled operator)
Counts compose the way Vim's do: 2d3w deletes six words.
In Visual mode the same letters operate on the selection: d (or x), y,
c (or s), >, <, u, U, ~, and r{char}.
## Text objects

├────────────┼───────────────────────────────────────┤
│ iw / aw │ word (iW / aW for WORDs) │
│ i( i) ib │ inside parentheses (a… includes them) │
│ i{ i} iB │ inside braces │
│ i[ i] │ inside brackets │
│ i< i> │ inside angle brackets │

## Undo
┌───────────────────────┬─────────────────────────────────────────────┐
│ Key │ Does │
├───────────────────────┼─────────────────────────────────────────────┤
│ u │ undo │
│ <C-r> │ redo │

## Registers
┌───────────────────────────┬────────────────────────────────┐
│ Key │ Does │
├───────────────────────────┼────────────────────────────────┤
│ "{reg} before an operator │ use that register │

│ "Ayy │ append it to register a │
│ "ap │ paste register a │

Named registers are a-z; A-Z append. Numbered registers 1-9 are a
delete ring — each linewise or multi-line delete shifts the others down.

last yank or delete.
┃ Note: registers are internal to the editor. There is no system-clipboard
┃ provider yet, so "+ and "* don't reach your OS clipboard — use your
┃ terminal's own copy/paste for that.

## Line wrapping and long lines
With 'wrap' on (the default) a long line continues onto the next screen row.
With it off, the view scrolls horizontally to follow the cursor. j/k and
the scroll offset ('scrolloff') account for wrapped rows either way.
## Mouse
On by default ([ui] mouse). Click to move the cursor; wheel to scroll. Set
mouse = false to give the wheel back to your terminal's own scrollback.
## Markdown live rendering
<C-g> (or :markdown) toggles it on a markdown buffer. Markup is concealed
on every line except the one the cursor is on — **bold** renders bold,
- becomes •, [ ] becomes ☐ — so you can see the document and still
edit the source. Headings, emphasis, inline and fenced code, lists, task
lists, quotes, links and rules are covered.
One source line is always one display row, so nothing about cursor or scroll
position changes when you toggle it.
## Syntax highlighting
Tree-sitter, on by default, for: Rust, JSON, TOML, Lua, Markdown,
JavaScript (.js .jsx .mjs .cjs), TypeScript (.ts .mts
.cts), TSX, Python (.py .pyi) and Bash (.sh .bash).
Colors come from the active theme, so a highlighted buffer looks like part of
the UI rather than a second one — see Themes.

Search and Replace
on this page: Searching in a buffer · Pattern syntax · Substituting · :global · Project-wide find & replace · Quickfix
ctrlvim has its own Vim regex engine, written from scratch rather than
translated onto a general-purpose regex library. That matters because a DFA
engine physically cannot evaluate a backreference or a lookaround — under a
translation layer, \1 and \@= aren't missing features, they're unreachable
ones. Here they work.
The same engine backs /, ?, :s, :g, :vimgrep and the project-wide
find & replace panel, so a pattern you learn in one place works in all of them.

## Searching in a buffer
┌────────┬────────────────────────┐
│ Key │ Does │
├────────┼────────────────────────┤
│ /{pat} │ search forward │
│ ?{pat} │ search backward │
│ n / N │ next / previous match │
│ :noh │ clear the highlighting │
└────────┴────────────────────────┘
'hlsearch' highlights every match, 'ignorecase' and 'smartcase' apply
here as they do everywhere patterns do. \c and \C in the pattern override
them — that's what those atoms are for.
### Search offsets
A suffix after the closing delimiter says where to leave the cursor. It
doesn't change what matches, and n/N carry it along.
┌────────────────────┬────────────────────────────────────────┐
│ Suffix │ Leaves the cursor │
├────────────────────┼────────────────────────────────────────┤
│ /pat/e │ on the match's last character │
│ /pat/e+1 │ one past it │
│ /pat/s-2, /pat/b-2 │ two before the match's first character │
│ /pat/+2 │ two lines down, at the first non-blank │
└────────────────────┴────────────────────────────────────────┘
## Pattern syntax
### Magic levels
\v very magic, \m magic (the default), \M nomagic, \V very nomagic.
They can change mid-pattern.
▏ \v(foo|bar)+ very magic: fewest backslashes
▏ \(foo\|bar\)\+ the same, at the default magic level
▏ \Vhttp:// very nomagic: everything is a literal
### Atoms
┌────────────────────────────┬───────────────────────────────────────────────────────────────────┐
│ Pattern │ Matches │
├────────────────────────────┼───────────────────────────────────────────────────────────────────┤
│ \< / \> │ start / end of a word │
│ \w \s \d \a \l \u \x \o \h │ word, space, digit, alpha, lower, upper, hex, octal, head-of-word │
│ \W \S \D … │ the uppercase form of each is its complement │
│ [abc], [^abc], [a-z] │ a collection │
│ \(…\) │ a capture group (\%(…\) for a non-capturing one) │
│ \1 … \9 │ a backreference to that group │
│ \zs / \ze │ set where the match starts / ends, independent of what's tested │
│ \%23l │ only on line 23 │
│ \%>4v │ only past virtual column 4 │
└────────────────────────────┴───────────────────────────────────────────────────────────────────┘
### Quantifiers
┌─────────┬─────────────────────────────────────┐
│ Pattern │ Means │
├─────────┼─────────────────────────────────────┤
│ * \+ \? │ zero-or-more, one-or-more, optional │
│ \{n,m} │ between n and m, greedy │
│ \{-n,m} │ between n and m, non-greedy │
│ \{-} │ as few as possible │
└─────────┴─────────────────────────────────────┘
### Lookaround and atomic groups
┌───────────┬────────────────────────────────────────┐
│ Pattern │ Means │
├───────────┼────────────────────────────────────────┤
│ \(…\)\@= │ positive lookahead │
│ \(…\)\@! │ negative lookahead │
│ \(…\)\@<= │ positive lookbehind │
│ \(…\)\@<! │ negative lookbehind │
│ \(…\)\@> │ atomic group (no backtracking into it) │
└───────────┴────────────────────────────────────────┘
▏ foo\(bar\)\@! "foo" not followed by "bar"
▏ \(#\)\@<=\w\+ a word preceded by "#", without matching the "#"
▏ ^\s*\zs\w\+ the first word on a line, indentation excluded
## Substituting
▏ :%s/old/new/g every occurrence in the file
▏ :'<,'>s/\s\+$// strip trailing whitespace from the selection
▏ :1,20s/foo/bar/ first match on each of lines 1–20
▏ :s//new/ reuse the last search pattern
▏ :s repeat the last substitution
Flags: g replaces every match on a line (not just the first), i forces
a case-insensitive match. Confirm mode (c) is not implemented.
### The replacement language
┌─────────┬──────────────────────────────────────────────────┐
│ Token │ Inserts │
├─────────┼──────────────────────────────────────────────────┤
│ \0 … \9 │ that capture group │
│ & │ the whole match (\& for a literal &) │
│ ~ │ the previous replacement text (\~ for a literal) │
│ \r, \n │ a line break │
│ \t │ a tab │
│ \u / \l │ uppercase / lowercase the next character │
│ \U / \L │ uppercase / lowercase until \E │
│ \e, \E │ end a \U / \L span │
└─────────┴──────────────────────────────────────────────────┘
▏ :%s/\<\(\w\)\(\w*\)/\u\1\2/g Title Case Every Word
▏ :%s/get_\(\w\+\)/get\U\1/g get_foo → getFOO
▏ :%s/\(\w\+\)@\(\w\+\)/\2:\1/g swap around the @
## :global
Run a command on every line that matches a pattern:
▏ :g/TODO/d delete every line containing TODO
▏ :g/^$/d squash blank lines
▏ :v/error/d delete every line NOT containing "error"
▏ :g/fn /normal A // <-<Esc>
:g! is the same as :v. The default range is the whole file.

($XDG_CONFIG_HOME/ctrlvim/config.toml if that's set). There is no init.lua

Seed a fully commented starter file:
▏ make user-config
…or copy
docs/config.example.toml
from the repo. Every field has a sensible default, so a missing or partial

## Why TOML and not a config script
The split is declarative versus imperative. TOML expresses the wiring —
which options are set, which key runs which command, which event triggers
which command, which plugins to load. Anything that needs actual logic lives
in a plugin, which the config then refers to by name.
The bridge between the two is the Ex command. A keymap's rhs and an autocmd's
command are ordinary : commands, so a plugin contributes behavior by
registering :Format and the config just names it. Your config stays free of
embedded code without losing extensibility.
Everything the config declares is run through the engine as an Ex command, so
config gets exactly the semantics the : command line has — one code path, one
definition of what an option or a mapping means.

## [ui]
The editor shell itself.
▏ [ui]
▏ drawer = false # open the file drawer (Ctrl-B sidebar) on startup
▏ mouse = true # wheel scrolling; false gives the wheel back to the terminal
▏ icons = "auto" # "auto" | "nerd" | "text"
▏ theme = "Tokyo Night"
• icons — auto uses Nerd Font glyphs when one is detected, nerd
always does, text uses lettered chips.
• theme — any name from Themes. Omit it to leave whatever you
last picked with :colorscheme alone.
## [options]
Anything :set understands.
▏ [options]
▏ number = true
▏ relativenumber = true
▏ ignorecase = true
▏ smartcase = true
▏ hlsearch = true
▏ expandtab = true
▏ autoindent = true
▏ splitbelow = true
▏ splitright = true
▏ tabstop = 4
▏ shiftwidth = 4
▏ scrolloff = 5
▏ foldmethod = "indent"
▏ timeoutlen = 500
The rule is mechanical: true sets the option, false becomes its
no-prefixed form, and numbers and strings become name=value.
This table is untyped on purpose — every key becomes a :set argument, so
any option the engine gains works here immediately. See Options for
the full list.
## [keymaps]
Settings about the mapping table, as opposed to the entries in it.
▏ [keymaps]
▏ defaults = true # install the built-in mappings
▏ leader = " " # what <leader> expands to
defaults = false starts from an empty table, for a config that wants to
define every chord itself. To drop just a few, use [[unmap]].
leader applies at definition time, as in Vim — so it must be set before the
[[keymap]] entries that use it.
## [[keymap]]
One table per mapping.
▏ [[keymap]]
▏ lhs = "<leader>g"
▏ rhs = ":Find<CR>"
▏ desc = "Search the project"
▏
▏ [[keymap]]
▏ mode = "i"
▏ lhs = "jj"
▏ rhs = "<Esc>"
▏ desc = "Leave Insert mode"
▏
▏ [[keymap]]
▏ mode = "v"
▏ lhs = "<"
▏ rhs = "<gv"
▏ desc = "Outdent, keeping the selection"
• mode — "n" (default), "i", or "v".
• lhs / rhs — both use <...> notation: <leader>, <Space>,
<Esc>, <CR>, <Tab>, <S-Tab>, <C-x>, <A-x> (same as <M-x>),
<C-S-x>, <Up>, <C-Left>, <F5>, <Del>, <Home>.
• desc — what ? and the which-key popup show. Optional; an undescribed
mapping is listed by its right-hand side instead.
An lhs that doesn't parse is reported on the status line, not silently
ignored — a typo can't leave you with a dead key.
Binding an lhs that a built-in already uses replaces it.
## [[unmap]]
Remove a built-in mapping, so the key falls through to its Vim meaning.
▏ [[unmap]]
▏ mode = "n"
▏ lhs = "<leader>d"
## [[command]]
Define a : command as an alias for another command line. This is the escape
hatch that keeps the config declarative: expansion is an ordinary Ex command
line, so a [[command]] plus a [[keymap]] pointing at it is a complete
binding with no plugin involved.
▏ [[command]]
▏ name = "RunPython"
▏ expansion = "!python3 %:p"
▏
▏ [[command]]
▏ name = "RunJava"
▏ expansion = "!cd %:p:h && javac %:p && java %:t:r"
▏
▏ [[keymap]]
▏ lhs = "<leader>rp"
▏ rhs = ":RunPython<CR>"
▏ desc = "Run this Python file"

filename positions — see Ex Commands.
## [[autocmd]]

▏ pattern = "*.rs"
▏ command = "set expandtab"
▏
▏ [[autocmd]]
▏ event = "VimEnter"
▏ pattern = "*"
▏ command = "set number"

name. It defaults to "*".

│ Event │ Fires │
├──────────────┼──────────────────────┤

│ BufEnter │ on entering a buffer │
│ BufLeave │ on leaving one │

│ BufWritePost │ after one │

A directory holding an init.lua or init.vim.

## The Settings tab writes this file
The dashboard's Settings section (press 2 on the dashboard) toggles the
same values live — drawer-on-startup, mouse, icon mode, AI — and writes them

That write goes through a format-preserving TOML writer, so your comments,

## Runtime versus config
Anything you can put in [options] you can also :set at runtime, and vice
versa; the config just runs the same commands at startup. The same goes for
[[keymap]] (:nnoremap) and [[command]] (:command). Runtime changes
aren't persisted unless the Settings tab manages that field — put it in the
config file to make it stick.
## Debugging a config
• :map lists every Normal-mode mapping; ? shows the described table.
• :set {opt}? echoes an option's current value.
• A bad mapping or unknown command reports on the status line rather than
failing silently.
• An unrecognized [ai] device or precision falls back to the default
rather than refusing to start.

## Scope
:set writes to the layer that makes sense for the option; :setlocal and
:setglobal pick one explicitly. A local value of "unset" means "inherit the
global", so unsetting a local override restores the global value rather than
some sentinel.
• Buffer-local (with global fallback): tabstop, shiftwidth,
expandtab, autoindent, iskeyword
• Window-local (with global fallback): number, relativenumber, wrap,
scrolloff, cursorline, foldenable, foldmethod, foldcolumn
• Global only: ignorecase, smartcase, hlsearch, splitbelow,
splitright, timeoutlen, guicursor

┌────────┬──────────────────────────────────────────────┐

### guicursor (gcr)
Cursor shape per mode. Default:
▏ n-v-c-sm:block,i-ci-ve:ver25,r-cr-o:hor20
Entries are modes:args, comma-separated. a means every mode. Later entries
win, which is what makes the idiomatic form work:
▏ :set guicursor=a:block,i:ver25
Recognized args: block, ver{N}, hor{N}, blinkon{N}, blinkoff{N}.
blinkwait and highlight-group names are accepted and ignored — they have no
meaning for a terminal cursor. Unparseable arguments are skipped rather than
failing the whole spec.
The {N} percentage is parsed and preserved so :set guicursor? echoes back
what you typed, but a terminal cursor can't actually be sized, so nothing
renders it.
### iskeyword
Which characters count as part of a word, for w/b/e, iw and \w.
Default @,48-57,_,192-255 (Neovim's).

Themes
on this page: Switching · The roster · What a theme defines · Adding a theme
ctrlvim ships seven themes. The whole UI reflows on a change — dashboard,
panels, status line, and syntax highlighting — because tree-sitter highlight
classes are styled from the active theme's palette rather than a second,
independent color table. A highlighted buffer looks like part of the editor,
not like a themed square pasted into it.
## Switching
▏ :colorscheme Gruvbox
▏ :colo Tokyo Night
▏ :colo " report the current theme
Names are case-insensitive. An unknown name reports
E185: Cannot find color scheme '…' and leaves the theme alone.
Or set it in your config:
▏ [ui]
▏ theme = "Tokyo Night"
Your choice is persisted to ~/.local/state/ctrlvim/theme and restored on
the next launch, so :colorscheme alone is enough to make a change stick. Set
[ui] theme only if you want the config file to be the authority; omitting it
leaves whatever you last picked alone.
## The roster
┌─────────────────┬───────────────────────────────────────────────────┐
│ Theme │ Is │
├─────────────────┼───────────────────────────────────────────────────┤
│ Terminal (Auto) │ (default) Follows your terminal's own theme │
│ Tokyo Night │ The night variant — deep blue-black, cool accents │
│ Catppuccin │ Soft pastel accents on a warm dark base │
│ Noir-cat │ A near-black base with Catppuccin accents │
│ Rosé Pine │ The main variant — muted rose and pine on plum │

### Terminal (Auto)
The default, and worth understanding: backgrounds and primary text use
Color::Reset — the terminal's own defaults — and accents map to the 16 ANSI
colors, so they track whatever palette your terminal is set to. Change your
terminal's theme and ctrlvim follows it, including light-background setups
that a hardcoded dark theme would be unreadable against.
The trade-off is that it can only be as good as your terminal's palette. If
your terminal's ANSI colors are unusual, pick one of the fixed themes instead.
## What a theme defines
Each theme is a flat set of roles rather than a highlight-group table:
┌────────────────────────────────────────┬─────────────────────────────────────────┐
│ Role │ Used for │
├────────────────────────────────────────┼─────────────────────────────────────────┤
│ bg, bg_dark, bg_highlight │ panel and editor backgrounds │
│ fg, fg_dim, fg_muted │ primary, dimmed and secondary text │
│ border, border_dim │ panel frames │
│ blue, cyan, green, purple, orange, red │ accents, and the syntax palette │
│ code_bg │ fenced code blocks in rendered markdown │
│ selection │ the Visual-mode selection │
│ search │ hlsearch matches │
└────────────────────────────────────────┴─────────────────────────────────────────┘
Syntax highlighting and markdown rendering both map onto those accents, which
is why every theme covers both without defining them.

Themes are compile-time constants in crates/ctrlvim-tui/src/theme.rs. Adding
one means adding a Theme const and listing it in ALL — that array is also
the picker/palette order. There is no runtime theme-file format yet.

linters — and can detect, install and (for linters) run them. The dashboard's
Settings tab is the front end for all of it.
┃ Scope note. There is no LSP client yet. ctrlvim detects and installs
┃ language servers and tracks an on/off flag for each, but nothing spawns one —
┃ so no completion, hover or go-to-definition from a server. Code navigation
┃ today comes from tree-sitter and from a tags file (<C-]>, :tag). The
┃ one tool category that actually runs is linters, via :Lint.

## Where installs go
I installs into ctrlvim's own tools directory — one subdirectory per tool:
▏ ~/.local/share/ctrlvim/tools/<name>/bin/
($XDG_DATA_HOME is honored.) Nothing is written outside that tree, and
removing a tool is rm -rf on its directory. rustup component add is the
exception: it installs into your rustup toolchain, where rust-analyzer belongs.
Detection checks PATH first, then the managed directory — so a tool you
already have installed system-wide is used as-is and never installed twice.
Installs run as background jobs. The editor stays responsive, and the row
updates when the job finishes.

## :Lint
Run the linter for the current buffer's filetype and fill the
quickfix list with its diagnostics.
▏ :Lint " or :lint
▏ :copen " see the results
▏ :cnext " walk them
┌──────────┬────────────┐
│ Filetype │ Linter │
├──────────┼────────────┤
│ sh, bash │ shellcheck │
│ python │ ruff │
└──────────┴────────────┘
Both definitions are ports of the real nvim-lint entries — the same
invocation and the same output parser (shellcheck's JSON1, ruff's JSON),
implemented natively in Rust rather than executed as Lua. Severities map onto
quickfix's error / warning / note.
The buffer's live content is piped to the linter on stdin, so you lint what
you're looking at, not the last thing you saved.
┃ One documented gap: ctrlvim always pipes stdin to shellcheck, where real
┃ nvim-lint passes a filename when the buffer has one. A script that sources
┃ a sibling file via shellcheck's SCRIPTDIR directive won't resolve it.
Adding a linter means porting its real nvim-lint definition: the invocation
and the output parser. See crates/ctrlvim-tools/src/lint.rs.

Inline AI Suggestions
on this page: It's off at two levels · Keys · Commands · Disk and memory · Speed · Full configuration · How it fits together
ctrlvim can propose code as you type, Copilot-style: grey ghost text ahead of
the cursor that <Tab> accepts and the next keystroke replaces. The model runs
locally and in-process — CodeGemma-2B on
candle. No API key, no network at edit
time, nothing leaving the machine.
It's fill-in-the-middle, so the model sees the code on both sides of the
cursor, not just what came before it.
┃ The repo's docs/ai.md
┃ is the exhaustive version of this page, including the model internals.
──────────────────────────────────────────────────────────────────────────
## It's off at two levels
Both have to be switched before a suggestion can appear.
### 1. Build it in
▏ cargo build -p ctrlvim --release --features ai # CPU
▏ cargo build -p ctrlvim --release --features ai-cuda # NVIDIA
▏ cargo build -p ctrlvim --release --features ai-metal # Apple silicon
ai-cuda and ai-metal imply ai — you don't need both flags.
candle and its dependency tree are minutes of compile time, which is too much
to charge every build for a feature that's also off at runtime. A binary built
without it still shows the settings row and still answers :AI; suggestions
just report "built without the local-model feature" rather than silently
never appearing.
Build in release. candle's quantized kernels are roughly an order of
magnitude slower unoptimized — a debug build cannot finish a completion in
reasonable time.
### 2. Switch it on
Three ways:
• Settings tab — Dashboard → 2, then the Inline AI suggestions row:
Enter/Space, or a from anywhere on the tab. This is the persistent one:
it writes [ai] enabled back to your config, so the choice survives a
restart. The checkbox tracks whether suggestions are actually running, not
just what the file says.
• :AI — toggles for this session only (:AI on / :AI off to be
explicit).
• The config file:
▏ [ai]
▏ enabled = true
Toggling it off drops the worker thread and the loaded weights. Toggling it
back on reloads from the local cache — no re-download.

## Disk and memory
By default ctrlvim loads a 4-bit quantized GGUF — the same 1.6 GB file
Ollama's codegemma:2b tag ships.
┌──────────────────────────┬─────────┬─────────────────────┐
│ File │ Size │ Used by default │
├──────────────────────────┼─────────┼─────────────────────┤
│ codegemma-2b-Q4_K_M.gguf │ 1.63 GB │ yes │
│ model.safetensors, bf16 │ 5.01 GB │ only with gguf = "" │
└──────────────────────────┴─────────┴─────────────────────┘
Resident memory is ~2.8 GB: the 1.6 GB of weights plus a 1.05 GB f16 embedding
table (Gemma's vocabulary is 256,000 tokens, so that table is large no matter
how the weights are quantized).
Other quantizations work — anything in a Gemma-1 GGUF repo:
▏ [ai.model]
▏ gguf = "bartowski/codegemma-2b-GGUF:codegemma-2b-Q5_K_M.gguf" # 1.84GB, better
▏ gguf = "bartowski/codegemma-2b-GGUF:codegemma-2b-Q3_K_M.gguf" # 1.38GB, worse
▏ gguf = "~/models/codegemma-2b-Q4_K_M.gguf" # a local file
▏ gguf = "" # full precision
┃ Gemma-2, Gemma-3 and Llama GGUFs will not load. This is a Gemma-1
┃ decoder, written because candle-transformers ships quantized_gemma3 and
┃ nothing for Gemma-1.
### The license gate
google/codegemma-2b is a gated repository. The shipped defaults avoid it
entirely — weights come from an ungated GGUF repo and tokenizer.json from an
ungated mirror — so this only bites if you point repo back at Google's. To do
that, accept the license at
https://huggingface.co/google/codegemma-2b and make a token available
(huggingface-cli login, or export HF_TOKEN). Without it the load fails with
a 401/403, and :AIStatus says so in words rather than a bare status code.
To skip the network entirely:
▏ [ai.model]
▏ path = "~/models/codegemma-2b"
That directory needs config.json, tokenizer.json and the .safetensors
shards — exactly what huggingface-cli download leaves behind.

## Speed
Be realistic about this on a CPU. Measured on a 4-core laptop, quantized, ~20
lines of context:
┌──────────────────────────────┬───────────────┐
│ │ Cost │
├──────────────────────────────┼───────────────┤
│ Prompt prefill (~200 tokens) │ ~35 s │
│ Each generated token │ ~0.45 s │
│ Model load (cached weights) │ a few seconds │
└──────────────────────────────┴───────────────┘
Prefill dominates, and it scales with how much context you send — which is
why context_before defaults to 20 lines rather than something generous.
Doubling the context roughly doubles time-to-first-suggestion.
If it's too slow, in order of effect:
1. Build with GPU support (ai-cuda / ai-metal). By far the biggest win.
2. Build in release mode.
3. Shrink the context — context_before = 10.
4. Lower max_tokens — you rarely accept more than a line or two anyway.
### Why it doesn't make the editor sluggish
Inference is confined to cores - 1 threads. candle parallelizes across every
core it can find, and a 2B model keeps them all busy for seconds at a time —
which made the whole editor feel slow, not just the suggestions. Leaving one
core for the UI thread costs a little completion speed and buys back a
responsive editor.
The other protections: a completion is only requested once typing pauses
(debounce_ms), only one is ever in flight, a newer request abandons the older
one mid-token, and max_millis caps any single attempt.

## Full configuration
Every key is optional; these are the defaults.
▏ [ai]
▏ enabled = false # off until you ask
▏ device = "auto" # auto | cpu | cuda | cuda:1 | metal
▏ debounce_ms = 350 # idle time before a completion is requested
▏ max_tokens = 64 # generation ceiling
▏ max_millis = 8000 # wall-clock ceiling for one completion
▏ temperature = 0.0 # 0 = greedy, which is what code completion wants
▏ top_p = 0.0 # nucleus sampling; 0 disables it
▏ repeat_penalty = 1.1 # 1.0 disables it
▏ repeat_last_n = 64 # window the penalty looks back over
▏ seed = 0
▏ context_before = 20 # lines before the cursor (the prefill cost)
▏ context_after = 6 # lines after
▏ max_prefix_chars = 1200 # hard caps, so one huge line can't blow the budget
▏ max_suffix_chars = 400
▏ max_lines = 8 # most lines of ghost text to display
▏ # threads = 3 # default: one fewer than the machine has
▏
▏ [ai.model]
▏ gguf = "bartowski/codegemma-2b-GGUF:codegemma-2b-Q4_K_M.gguf"
▏ repo = "unsloth/codegemma-2b"
▏ revision = "main"
▏ precision = "bf16" # bf16 | f16 | f32; ignored when `gguf` is set
▏ # path = "~/models/codegemma-2b"
max_lines = 1 is worth knowing about. Continuation rows of a multi-line
suggestion are drawn over the buffer rows below the cursor — one source line
is one screen row in this TUI, so there's nowhere to push the real text down
to. They're shaded to read as an overlay and vanish on accept or dismiss, but
if you'd rather never see it, keep suggestions strictly inline.
An unrecognized device or precision falls back to the default rather than
costing you your editor.

## How it fits together
Same split as the quickfix list and the tag table — the engine owns the data,
the host owns the I/O:
• ctrlvim-editor (suggest.rs) owns what's being suggested, where it's
anchored, when it goes stale, and what accepting part of it does to the
buffer. It has never heard of candle. Every context change bumps a sequence
number a reply must still match to be shown, which is what stops a completion
for three keystrokes ago appearing at the new cursor.
• ctrlvim-ai owns the model, the weights, and the thread they run on. It
has never heard of buffers or cursors.
• ctrlvim-tui joins them: debounce, submit, poll, draw.

Plugins and Scripting
on this page: Where plugins live · The plugin manager · The Lua API · Vimscript · Running scripts by hand · Registering a command · Async and jobs · msgpack-RPC · Writing your first plugin
Behavior that needs actual logic goes in a plugin; your
config file then refers to it by name. The bridge is the Ex
command — a plugin registers :Format, and a [[keymap]] or [[autocmd]]
just names it.
Plugins are written in Lua (via mlua, with Lua 5.4 vendored) or
Vimscript (there's a native interpreter).
──────────────────────────────────────────────────────────────────────────
## Where plugins live
Two conventions, and they do different things.
### pack/*/start/* — the search path
▏ ~/.config/ctrlvim/pack/<group>/start/<plugin>/
▏ ~/.config/ctrlvim/pack/<group>/opt/<plugin>/ (lazy)
Every start/* directory goes on the require() search path
unconditionally, matching Neovim's own native package loading. This makes a
plugin's lua/ tree resolvable; it does not source it. A
library-shaped plugin (no init.lua, e.g. nvim-lspconfig) never gets
sourced by anything — it's there for whatever require()s it.
opt/* directories are lazy, as in Neovim.
### [[plugin]] — what actually loads
▏ [[plugin]]
▏ name = "example"
▏ path = "~/.config/ctrlvim/pack/example"
▏ event = "BufWritePre" # omit to load at startup
▏ enabled = true
ctrlvim sources path/init.lua if present, else path/init.vim. Load order
is the order declared in the file — which is why there's no runtimepath
search: what loads, and when, is explicit rather than emergent.
event defers loading until that event first fires (VimEnter, BufEnter,
BufLeave, BufWritePre, BufWritePost). enabled = false keeps the plugin
declared but unloaded.
path also goes on the require() search path, so a plugin can require()
its own submodules.
## The plugin manager
:plugins (also :Plugins, :Lazy, or p from the dashboard) opens a
full-width table of every plugin found under pack/, with load status and
whether an update is available. It's a status view — installing and removing
plugins is still git clone into pack/*/start/ and an entry in your config.

## Registering a command
The cleanest way for a plugin to contribute behavior, because a command is
what a keymap and an autocmd can both name:
▏ vim.api.nvim_create_user_command('Format', function()
▏ vim.cmd('!stylua ' .. vim.api.nvim_buf_get_name(0))
▏ end, {})
▏ [[keymap]]
▏ lhs = "<leader>f"
▏ rhs = ":Format<CR>"
▏ desc = "Format this file"
:command Name {expansion} does the same thing for the pure-alias case, with
no Lua at all. :comclear removes every user-defined command.

## Async and jobs
Long-running work goes through the job system rather than blocking the editor
— that's how :make, :grep, :Lint and tool installs all behave. A spawned
program's output streams in as it arrives.
vim.uv (aliased vim.loop) exposes timers, pipes and process handles on the
same Tokio-backed event loop.
## msgpack-RPC
ctrlvim-async implements a msgpack-RPC server over a Unix socket that
dispatches to the same API surface Lua uses, so an external client can drive
the editor programmatically. The ctrlvim-core demo binary
(cargo run -p ctrlvim-core) exercises it.
Note that the cvi TUI does not currently start a listener — the RPC
server is a library capability, not yet an editor feature.

## The shape of it
Neovim's C core is a mountain of complexity. ctrlvim reimplements it in
memory-safe Rust, one concern per crate, keeping what makes Vim good — modal
editing, extensibility, terminal-native feel — while making the internals
approachable.

## The one invariant that explains most of the code
The engine owns the data; the host owns the I/O.
ctrlvim-editor is UI-less. It can move the cursor for :5 itself, but
anything touching the filesystem, the window list, or process lifetime is
emitted as an ExEffect for the frontend to carry out. The engine decides
what should happen; the host does it.
▏ :w → ExEffect::Write { force } → host writes the file
▏ :e → ExEffect::Edit(path) → host opens the buffer
▏ :! → ExEffect::Shell(cmd) → host spawns the process
The same split recurs everywhere:
• Quickfix — the engine owns the list and the current index; the host runs
make and opens files.
• Tags — the engine owns the stack; the host reads the tags file.
• Pins — the engine owns the ordered list; the host opens the file and
draws the picker.
• AI — the engine owns what's suggested, where it's anchored, and when it
goes stale; ctrlvim-ai owns the model and its thread; the TUI joins them.
This is what makes the editor testable without a terminal, and it's why
"editor logic belongs in the engine" is a rule rather than a preference —
shortcutting a feature into the TUI makes it unlistable, unbindable and
untestable.
## Everything is an Ex command
The frontend's own actions — the palette, the drawer, the plugin manager, the
help modal — are Ex commands (ExEffect::HostAction), not hardcoded key
handlers. That's what makes <leader>p → command palette expressible at all,
and what lets ? list it.
Likewise, built-in mappings are data (DEFAULT_KEYMAPS) that goes through the
same Keymap::set_with_desc your config uses. There is exactly one place a
mapping's description can live, so the keybinding help can never disagree with
the table.
And config is executed as Ex commands: [options] becomes :set,
[[keymap]] becomes :nnoremap, [[command]] becomes :command. One code
path, one definition of what an option means.
## Rendering
The TUI redraws on each event. Two things dominate the per-keystroke cost:
• Tree-sitter reparse. Highlighting is windowed to the viewport and
query compilation is cached. Incremental parsing is not done yet, so a full
reparse still happens on edit.
• Optimization level. The dev profile builds the C-heavy dependencies
(tree-sitter grammars, ropey) optimized even in debug builds, because
unoptimized they make the editor unusable.
Two invariants worth knowing before touching startup or theming:
1. Project data gathers off-thread. Git status, file listing and session
history never block the first frame (~2 ms).
2. theme::bg() is Color::Reset under the default Terminal theme, so it
must never be used as a foreground. Use theme::on_accent().
## Testing
cargo test --workspace. The engine's tests drive a Session by feeding keys
and asserting on buffer state and emitted effects — no terminal involved. A few
structural tests enforce the invariants above, e.g. that every command the
parser dispatches is in the palette catalog, that no two commands claim the
same abbreviation, and that every catalog entry has a description.
